## 这一阶段要搞懂什么

调度器是 mini-sglang 的心脏。它每一轮都要回答两个问题：这一批算哪些请求、每个请求算几个 token；算完之后，谁结束了、资源怎么回收。读完这一章，你应该能不看代码回答：

- 一个新请求什么时候能被接纳？放不下时会发生什么？
- 一个 8,000 token 的 prompt 怎么被切成几块分批算？
- 为什么一个 batch 要么全是 prefill、要么全是 decode？
- overlap 模式下 CPU 为什么能领先 GPU 一拍？代价是什么？

建议先读顺序执行的 `normal_loop`，看懂之后再读 `overlap_loop`。两者只差几行，但差的那几行正是本章最难的部分。

## 讲解

### 一轮循环：收消息、选批、前向、收尾

<SrcCode path="scheduler/scheduler.py" sym="Scheduler.normal_loop" />

每一轮做四件事：

1. **收消息**。只有手上完全没活（没有待 prefill 的请求，也没有在 decode 的请求；overlap 模式下还要求没有等着收尾的上一批）时才阻塞等待，否则把队列里已有的消息一次取完就走。新请求在 <Src path="scheduler/scheduler.py" sym="Scheduler._process_one_msg" /> 里先检查长度：prompt 长度达到 `max_seq_len` 的直接丢弃，`max_tokens` 超出剩余长度的被截短，然后放进 prefill 的等待队列。
2. **选批**，由 <Src path="scheduler/scheduler.py" sym="Scheduler._schedule_next_batch" /> 决定，下一节细讲。
3. **前向**：`_forward` 把 batch 交给引擎，拿回采样出的 token。
4. **收尾**：`_process_last_data` 判断谁结束了、回收资源、把新 token 发给反分词器。

`normal_loop` 里第 3 步和第 4 步处理的是同一批，这就是「顺序执行」。

### 选批：prefill 优先，整批同类型

<SrcCode path="scheduler/scheduler.py" sym="Scheduler._schedule_next_batch" />

策略只有一行：先问 prefill 队列能不能凑出一批，能就整批都是 prefill；凑不出来才把所有正在 decode 的请求打成一批。所以同一个 batch 里不会混着 prefill 和 decode。

代价是延迟抖动：一个长 prompt 进来时，所有正在 decode 的请求都要等这一批 prefill 算完才能出下一个 token。代码里的 TODO 也写着以后要支持别的策略。decode 批按 `uid` 排序，是为了让多卡的 batch 顺序一致，<StageLink id="s9" /> 会讲。

### 准入控制：按 `max_tokens` 保守预留

新请求能不能进入 prefill，由 `PrefillAdder._try_allocate_one` 判断：

<SrcCode path="scheduler/prefill.py" sym="PrefillAdder._try_allocate_one" mark={['estimated_len = extend_len + req.output_len']} />

逐行看：

- 先要有空闲的表行（`table_manager.available_size`），也就是 `max_running_req` 限制的并发数，默认 256。
- `match_req` 去前缀缓存里找最长的已缓存前缀（<StageLink id="s6" /> 细讲），命中的部分不用重算。
- **关键在 `estimated_len`**：它等于「还要算的 prompt 长度」加上 `output_len`，而 `output_len` 就是 `max_tokens`。调度器按每个请求**最多**会生成多少 token 来预留 KV 空间，不管它实际会不会提前遇到 EOS。
- `reserved_size` 是已经承诺出去的空间。它的初值是 <Src path="scheduler/decode.py" sym="DecodeManager.inflight_tokens" />：所有在跑的 decode 请求还剩多少 token 没生成（`page_size > 1` 时每个请求再多留不满一页的空间）。每接纳一个新请求，就再加上它的剩余长度和 `max_tokens`。
- 为什么要检查两次？`available_size` 等于「空闲页」加上「前缀缓存里可以驱逐的部分」。`lock` 会把命中的前缀从「可驱逐」挪到「受保护」，可用空间随之变小，所以加锁后必须再查一遍；放不下就解锁返回。

放不下的请求会怎样？<Src path="scheduler/prefill.py" sym="PrefillManager.schedule_next_batch" /> 按先来先服务的顺序遍历等待队列，遇到第一个放不下的就 `break`，它和它后面的请求都留在队列里等下一轮。mini-sglang **没有抢占**：已经在跑的请求不会被踢出去给新请求腾地方，代价就是上面这种保守预留。

<Aside type="note" title="算一笔账：max_tokens 直接决定并发上限">
在 RTX 4080 SUPER 上用默认参数启动，实测 KV 池有 112,081 个 token。按上面的准入公式算：如果每个请求的 prompt 是 1,000 个 token、`max_tokens=1024`，每个请求要预留 2,024 个 token，最多同时接纳 55 个（55 × 2,024 = 111,320），哪怕它们实际只生成几十个 token 就结束了。55 这个数是算出来的，没有实测。
</Aside>

### Chunked prefill：长 prompt 分块算

接纳之后，`_add_one_req` 决定这一批给它算多少：

<SrcCode path="scheduler/prefill.py" sym="PrefillAdder._add_one_req" />

- 每一批有一个 token 预算 `token_budget`，初值是 `max_extend_tokens`（默认 8,192）。一个请求这次最多算 `min(预算, 剩余 prompt 长度)` 个 token。
- 算不完就用 `ChunkedReq` 表示。它的 `can_decode` 恒为 False，`append_host` 直接抛异常：只算了一部分 prompt，最后一个位置的 logits 并不预测真正的下一个 token。GPU 上照样会对它采样（整批一起采），但结果写进 -1 列丢掉，收尾时也直接跳过。
- 这一块 prompt 的 token id 被非阻塞地拷进 GPU 上的 `token_pool`。模型的输入永远从 `token_pool` 读，<StageLink id="s2" /> 讲过这张表。
- 回到 `PrefillManager.schedule_next_batch`，被切块的请求会被放回等待队列的**最前面**；下一轮 `try_add_one` 发现它带着 `chunked_req`，就沿用原来的表行和缓存句柄，从新的 `cached_len` 接着切，不再重新走准入检查。

<Aside type="note" title="实测：100 个 token 的 prompt，预算 16">
把 `prefill_budget` 改成 16 后跑一个 100 个 token 的 prompt，记录每批的请求类型、`cached_len` 和 `extend_len`：

```text
[ChunkedReq, 0, 16]  [ChunkedReq, 16, 16]  [ChunkedReq, 32, 16]  [ChunkedReq, 48, 16]
[ChunkedReq, 64, 16]  [ChunkedReq, 80, 16]  [Req, 96, 4]
```

前 6 块的采样结果都被丢掉，第 7 块只剩 4 个 token，变成普通的 `Req`，算完采样出第一个输出 token。
</Aside>

### 准备一个 batch：六样东西

选出 batch 之后、交给 GPU 之前，`_prepare_batch` 要把它翻译成模型能直接用的张量：

<SrcCode path="scheduler/scheduler.py" sym="Scheduler._prepare_batch" />

1. `pad_batch`：decode 批要补齐到某个录过 CUDA graph 的大小，补的是指向哑页的 dummy 请求（<StageLink id="s7" />）。
2. `allocate_paged`：给每个请求这次要写的位置 `[cached_len, device_len)` 分配 KV 槽位，写进 `page_table`（<StageLink id="s4" />）。
3. `positions`：每个请求的 `arange(cached_len, device_len)` 拼起来，给 RoPE 用。
4. `input_tuple`：每个输入 token 属于哪一行、在第几列。用它查 `token_pool` 得到 `input_ids`，查 `page_table` 得到 `out_loc`（新 KV 写到哪）。
5. `write_tuple`：采样出的 token 写回 `token_pool` 的哪一行、哪一列。列号是 `device_len`；不能继续生成的请求（典型的是 `ChunkedReq`）写 -1。负下标会落到这一行的最后一列，而输入位置最大只到 `max_seq_len − 2`，那一列永远不会被当作输入读到，相当于丢弃。
6. attention 后端的 metadata 和采样参数。

注意第 4 步：`input_ids` 是在 GPU 上从 `token_pool` 查出来的，不是从 CPU 上的 `Req.input_ids` 拷过去的。上一批采样出的 token 由 GPU 直接写进 `token_pool`，下一批直接从那里读，中间不用经过 CPU。这是 overlap 能成立的前提。

### 前向与收尾

<SrcCode path="scheduler/scheduler.py" sym="Scheduler._forward" />

三件事：从 `token_pool` 查出输入、跑模型并采样、把采样结果写回 `token_pool`。最后一行 `filter_reqs` 把这批里还能继续生成的请求并进 decode 集合：刚做完 prefill 的请求就是在这里加入 decode 的，生成到 `max_tokens` 的请求也是在这里离开的。

还有一处容易漏看：<Src path="engine/engine.py" sym="Engine.forward_batch" /> 在**发射**完 kernel 之后，马上对每个请求调用 `complete_one`：`cached_len` 追到 `device_len`，`device_len` 再加一。decode 批里两者各前进一格，prefill 批里 `cached_len` 一次跨过整段刚算的 prompt。CPU 这边的长度记账比 GPU 的实际计算先走一步。

<SrcCode path="scheduler/scheduler.py" sym="Scheduler._process_last_data" mark={['if finished and req not in self.finished_reqs:']} />

收尾时，先等这批 token 拷回 CPU（`copy_done.synchronize()`），然后逐个请求：

- `ChunkedReq` 直接跳过，它的采样结果没有意义。
- 结束条件有两个：到了 `max_tokens`（`not req.can_decode`），或者采到了 EOS（除非设了 `ignore_eos`）。
- 不管结束没有，都发一条 `DetokenizeMsg` 给反分词器。
- 结束的请求从 decode 集合里删掉，由 `_free_req_resources` 还回表行，并把 KV 交给前缀缓存：能插进树的部分留在树里，剩下的尾巴直接释放（<StageLink id="s6" />）。
- 没结束、但这批是 prefill 的请求，调用 `cache_req(finished=False)`：把刚算完的 prompt 提前插进前缀缓存，同一时刻进来的相同前缀的请求就能直接复用。

`lazy_free_region` 只是把这一轮所有的释放攒起来，最后用一次 `torch.cat` 并回空闲列表，省得每释放一个请求就拼一次张量。它**不会**把释放推迟到 GPU 算完之后，这一点在下面很重要。

### Overlap：CPU 领先 GPU 一拍

<SrcCode path="scheduler/scheduler.py" sym="Scheduler.overlap_loop" mark={['self.engine.stream.wait_stream(self.stream)', 'self._process_last_data(last_data)']} />

和 `normal_loop` 相比，只有两处不同：

- 前向放在引擎自己的 CUDA stream 上跑，发射前 `engine.stream.wait_stream(self.stream)`，让引擎 stream 等调度器 stream 上已经排队的拷贝（positions、映射表、`page_table`、metadata）全部完成。
- 收尾处理的是**上一批** `last_data`，而且放在发射当前批**之后**。

于是时间线变成这样：GPU 在算第 N 批的时候，CPU 已经调度并发射了第 N+1 批，然后回头等第 N 批的结果、做收尾；收尾一结束又去调度第 N+2 批。GPU 算完第 N 批时，第 N+1 批已经排在它的队列里，几乎不用停下来等 CPU。

为什么 CPU 不等第 N 批的结果就能调度第 N+1 批？因为调度只需要**长度**，不需要**内容**：`complete_one` 在发射时就把长度推进了，下一批的输入 token 由 GPU 从 `token_pool` 里读，按 stream 的顺序一定排在第 N 批的写入之后。

CPU 唯一不知道的，是第 N 批里有没有请求采到了 EOS。所以一个其实已经结束的请求，会被照常排进第 N+1 批，多算一步：

| 轮次 | 发射的批 | 收尾的批 | 请求 R 的情况 |
| --- | --- | --- | --- |
| j | 第 j 批，R 在里面 | 第 j−1 批 | 第 j 批给 R 采到了 EOS，但 CPU 还不知道 |
| j+1 | 第 j+1 批，R **仍然**在里面 | 第 j 批 | 发现 EOS，把 R 移出 decode 集合，释放表行和 KV，记进 `finished_reqs` |
| j+2 | 第 j+2 批，R 不在了 | 第 j+1 批 | R 在 `finished_reqs` 里，跳过第二次释放 |

按 `max_tokens` 结束的请求不会多算：长度 CPU 是知道的，最后一批发射后 `can_decode` 变成 False，`filter_reqs` 当场把它移出 decode 集合。但它有另一种错位。`finished` 是收尾时按 `can_decode` 算的，而收尾第 N 批的时候，第 N+1 批已经发射，`complete_one` 已经把长度又推进了一格。于是结束标志早到了一个 token：

| 轮次 | 发射的批 | 收尾的批 | 请求 R 的情况（`max_tokens` 为 M） |
| --- | --- | --- | --- |
| M | 第 M 批，R 的最后一步，发射后 `can_decode` 变成 False | 第 M−1 批 | `finished` 已经为真：在倒数第二个 token 上判定结束，释放表行和 KV，记进 `finished_reqs` |
| M+1 | 第 M+1 批，R 不在了 | 第 M 批 | R 在 `finished_reqs` 里，跳过第二次释放；最后一个 token 又带着 `finished=True` 发出去一次 |

两张表都有一个前提：下一轮排出来的是 decode 批。调度是 prefill 优先的，如果那一轮正好有新请求凑成了 prefill 批，R 就不在里面。以 EOS 结束时不会多算那一步；以 `max_tokens` 结束时长度不会被提前推进，结束标志照常。这时 R 在下一轮收尾时才被发现结束，唯一还没执行完的是它上一批自己的 `token_pool` 写入，排在 `copy_done` 之后、紧接着就会执行。下面的实测只留了 1 个表行，新请求要等 R 释放才进得来，插不进 prefill 批，所以每次都会碰上；真实负载下两种情况都会出现。

两种情况都靠 `finished_reqs` 防住重复释放。它只保存上一轮结束的请求，因为 CPU 只领先一拍，请求释放之后最多还有一批要收尾。代码注释里的「may make the request freed twice」说的就是这件事。

### 结束的请求，还留下了两个问题

`finished_reqs` 防住了重复释放，但还有两件事代码没有拦：

1. **多出来的回复**。以 EOS 结束时，第 j+2 轮收尾照样给多算的那一步生成一条 `DetokenizeMsg`：这个 token 是 EOS **之后**采样出来的，`finished` 通常是 False，会被当作正常输出发出去。以 `max_tokens` 结束时，则是连着两条 `finished=True`。
2. **迟到的写入**。R 的表行还回去的时候，还有一批往这一行写的前向没有算完：以 EOS 结束时是多算的第 j+1 批，以 `max_tokens` 结束时就是 R 真正的最后一批，第 M 批。这一批的 `_forward` 早在发射时就排好了一次写入，把采样结果写进 `token_pool` 里 R 原来那一行的第 `device_len` 列。

第 2 点为什么危险？看这三件事分别在哪个 CUDA stream 上：

<SrcCode path="scheduler/scheduler.py" sym="_make_write_tuple" />

- 那一批末尾的写入在**引擎 stream** 上，要等这一批算完才执行。写哪一列在发射前就定了，条件是当时的 `can_decode`，所以按 `max_tokens` 结束的最后一批也会写。
- `TableManager.allocate` 用 `pop()` 取空闲行，后进先出，刚还回去的行会被**第一个**拿走。下一轮如果有新请求进来，它拿到的正是 R 那一行，并在**调度器 stream** 上把 prompt 拷进去（上面 `_add_one_req` 里的非阻塞 `copy_`；命中前缀时 `_try_allocate_one` 也会先拷一段）。
- `wait_stream` 只让引擎 stream 等调度器 stream，反方向没有任何同步。

所以新请求的 prompt 可能先拷进去，然后被迟到的写入覆盖掉一格。只要新请求的 prompt 比 R 的总长度长，这一格就落在它的 prompt 里。

<Aside type="caution" title="实测：两个问题都能稳定复现">
在 RTX 4080 SUPER 上，只留 1 个表行，先让请求 A（「1+1 等于几？只回答数字。」）以 EOS 结束，再让请求 B 复用这一行。B 是一道翻译题，prompt 在位置 27（从 0 数）的 token 正好是「电影」。

| | overlap 开 | overlap 关 |
| --- | --- | --- |
| A 的输出 | `'1\n'`（token 16、198） | `'1'`（token 16） |
| B 的 prefill 在位置 27 读到的 token | 198（换行符） | 100378（「电影」） |
| B 的译文 | `...and then watched together.` | `...and watched a movie together.` |

A 的 prompt 长 25，输出「1」和 EOS 占了位置 25、26，多算的那一步正好把采样结果写进位置 27。另一组实验把 B 换成 300 个随机 token 重复 5 次，开 overlap 时每次都是位置 27 被改成 198，关掉后一次都没有。

再让 A 改用 `SamplingParams(max_tokens=3, ignore_eos=True)`，按长度结束，它的最后一个 token 是 198。开 overlap 时 B 的位置 27 同样被改成 198，译文同样少了 movie；`max_tokens=4` 时被改的是位置 28（25 + 4 − 1）。`max_tokens=2` 那次没有撞上：这是一场竞争，不是每次都会输。关掉 overlap 后三次都正常。完整脚本见下面的动手实验。
</Aside>

**服务模式下，第 1 点会让回复少一个 token。** API server 的三条返回路径，也就是 `/generate` 的流式、`/v1/chat/completions` 的流式和非流式，读到第一条 `finished=True` 的回复就结束响应。所以按 `max_tokens` 结束的请求，只要最后两步是在相邻两轮发射的，最后一个 token 就到不了客户端。下面是同一个 prompt（`The capital of France is`）贪心解码、`ignore_eos=true` 的实测，启动参数见[实测记录](../../appendix/measurements/)。段数是 `/generate` 流式返回的 `data:` 行数（不算 `data: [DONE]`）；非流式的 `/v1/chat/completions` 显式传 `temperature=0` 时拿到的文本完全相同，它的默认温度是 1.0：

| `max_tokens` | overlap 开 | overlap 关 |
| --- | --- | --- |
| 1 | ` Paris`（1 段） | ` Paris`（1 段） |
| 2 | ` Paris`（1 段） | ` Paris.`（2 段） |
| 8 | ` Paris. The capital of Italy is`（7 段） | ` Paris. The capital of Italy is Rome`（8 段） |

`max_tokens=1` 不受影响：R 只出现在 prefill 那一批里，收尾时没有更新的一批替它推进过长度。

离线的 `LLM` 基本看不出这个问题，因为它把每条消息的 token 都收进输出，只丢掉带着结束标志的 EOS。例外是 `ignore_eos=True` 时倒数第二个 token 恰好是 EOS：它带着早到的结束标志，会被当成结尾的 EOS 丢掉。上面 `max_tokens=3` 那次，A 的输出就从 `[16, 151645, 198]` 变成了 `[16, 198]`。

以 EOS 结束时多出来的那条回复，在服务模式下也到不了客户端，但它不会消失。前端读到结束标志就 `break`，`wait_for_ack` 末尾删除 uid 的代码根本走不到，这条回复通常会被追加进 `ack_map`，再也没人读；反分词器也会给这个已经结束的 uid 新建一个 `DecodeStatus`，而且因为 `finished` 是 False，永远不会删除。<StageLink id="s8" /> 会讲这两处泄漏。第 2 点在服务模式和离线的 `LLM` 里都一样：只要开着 overlap、新请求又复用了刚释放的表行，就可能发生。

## 常见误区

- **「overlap 让 prefill 和 decode 并行」**：不是。GPU 上同一时刻只有一批在跑，重叠的是 CPU 的调度、收尾和 GPU 的计算。
- **「decode 请求每轮都要重新准入」**：不用。准入只发生在 prefill；进了 decode 集合的请求每轮都会被打进 decode 批，直到结束。
- **「`max_tokens` 只是个上限，设大一点没关系」**：它直接决定每个请求预留多少 KV，设得越大，能同时接纳的请求越少。
- **「chunked prefill 的每一块都会产出一个 token」**：只有最后一块会。前面的块都是 `ChunkedReq`，GPU 上照样采样，但结果写进 -1 列丢掉，收尾时也直接跳过。

## 自测题

1. `PrefillAdder` 的 `reserved_size` 初值是什么？每接纳一个请求加多少？为什么要这样算？

   <Answer>
   初值是 `decode_manager.inflight_tokens`：所有在跑的 decode 请求还剩多少 token 没生成，`page_size > 1` 时每个请求再加 `page_size − 1`。每接纳一个请求，加上它剩余的 prompt 长度和 `max_tokens`。这是在给每个已接纳的请求预留到 `max_tokens` 为止的全部空间，保证没有抢占也一定能跑完。
   </Answer>

2. 显存紧张时，新请求会怎样？已经在跑的请求会怎样？

   <Answer>
   新请求在准入时就被挡住，连同它后面的请求一起留在等待队列里（遇到第一个放不下的就 `break`），等别的请求结束、空间还回来。已经在跑的请求不受影响，mini-sglang 没有抢占。完整版 SGLang 用 retract 把请求撤回队列来腾空间。
   </Answer>

3. `_try_allocate_one` 为什么要在 `lock` 前后各检查一次可用空间？

   <Answer>
   可用空间包括前缀缓存里可以驱逐的部分。加锁会把命中的前缀从可驱逐变成受保护，可用空间随之减少。第一次检查是加锁前的快速判断，第二次才是准确的；如果加锁后放不下，就解锁返回 None。
   </Answer>

4. 同一个 batch 里会同时有 prefill 和 decode 请求吗？这样做的代价是什么？

   <Answer>
   不会。`_schedule_next_batch` 先尝试 prefill，有就整批都是 prefill，没有才跑 decode。代价是长 prompt 进来时，所有 decode 请求都要等这批 prefill 算完，出 token 的间隔会突然变长。
   </Answer>

5. 为什么模型的输入要从 GPU 上的 `token_pool` 读，而不是直接用 `Req.input_ids`？

   <Answer>
   `Req.input_ids` 在 CPU 上，而且 overlap 模式下调度第 N+1 批时，第 N 批的 token 还没拷回 CPU。从 `token_pool` 读，第 N 批采样出的 token 由 GPU 直接写进去、第 N+1 批直接读出来，按 stream 顺序天然正确，CPU 不用等。
   </Answer>

6. 服务模式下（overlap 默认开着），一个 `max_tokens=8`、`ignore_eos=true` 的请求只拿回 7 个 token。结束标志是在哪一步提前的？为什么离线的 `LLM` 能拿到 8 个？

   <Answer>
   收尾第 7 批时，第 8 批已经发射，`complete_one` 把 `device_len` 推进到了 `max_device_len`，`can_decode` 变成 False，于是第 7 个 token 就带上了 `finished=True`，请求在这时被释放；第 8 个 token 在下一轮收尾时又带一次 `finished=True`（`finished_reqs` 挡住了第二次释放，没挡住这条回复）。API server 读到第一条结束标志就结束响应，第 8 个 token 到不了客户端。离线的 `LLM` 把每条消息的 token 都收进输出，两条都收，所以是完整的 8 个。
   </Answer>

7. prefill 批里没有结束的请求，为什么要调用 `cache_req(finished=False)`？

   <Answer>
   把刚算好的 prompt 前缀提前插进前缀缓存，并换成锁住新 handle。这样在它 decode 的同时，新来的、带相同前缀的请求（比如同一个 system prompt）就能直接命中，不用等它结束。
   </Answer>

8. 进阶：迟到的写入为什么能改写新请求的 prompt？两次写入分别在哪个 stream 上？

   <Answer>
   以 EOS 结束为例，迟到的写入是第 j+1 批 `_forward` 里的 `self.token_pool[output_mapping] = forward_output.next_tokens_gpu`，在引擎 stream 上，要等那一批算完才执行。新请求的 prompt 拷贝在 `_add_one_req` 里（命中前缀时 `_try_allocate_one` 还会先拷一段），在调度器 stream 上。R 的表行在第 j+1 轮就还回去了，`TableManager` 后进先出，第 j+2 轮的新请求正好拿到这一行。`wait_stream` 只让引擎 stream 等调度器 stream，调度器 stream 上的拷贝不会等引擎 stream 上还没执行的写入，于是拷贝可能先完成、再被覆盖。按 `max_tokens` 结束时，迟到的是 R 真正的最后一批（第 M 批），表行在第 M 轮还回去，道理一样。
   </Answer>

## 动手实验

<Steps>

1. **画时间线。** 合上代码，在纸上画 CPU 和 GPU 两条时间线，分别画 `normal_loop` 和 `overlap_loop`，标出第 N 批的发射、第 N 批结果的收尾、第 N+1 批的调度各在什么时候。再对照上面的时间线图检查。

2. **看 chunked prefill 怎么切块。** 在 `PrefillManager.schedule_next_batch` 返回前打印每个请求的类型、`cached_len` 和 `extend_len`，然后把预算调小：

   ```python
   from minisgl.core import SamplingParams
   from minisgl.llm import LLM

   llm = LLM(
       "Qwen/Qwen3-0.6B",
       attention_backend="fi",
       max_seq_len_override=4096,
       cuda_graph_max_bs=8,
       memory_ratio=0.5,
   )
   llm.prefill_budget = 16  # 每批 token 预算，默认 max_extend_tokens
   llm.generate([list(range(1000, 1100))], SamplingParams(max_tokens=4))
   ```

   先自己预测会切成几块、每块多长，再跑。上面的实测框里有答案。

3. **复现结束请求的两个问题。** 下面的脚本只留 1 个表行，让 B 必须复用 A 刚释放的那一行。分别直接运行、以及加上 `MINISGL_DISABLE_OVERLAP_SCHEDULING=1` 运行，对比输出：

   ```python title="probe_eos.py"
   from minisgl.core import SamplingParams
   from minisgl.llm import LLM

   llm = LLM(
       "Qwen/Qwen3-0.6B",
       attention_backend="fi",
       max_running_req=1,  # 只有 1 个表行，B 只能复用 A 的那一行
       cache_type="naive",
       max_seq_len_override=4096,
       cuda_graph_max_bs=1,
       memory_ratio=0.5,
   )

   def chat(text):
       return llm.tokenizer.apply_chat_template(
           [{"role": "user", "content": text}],
           add_generation_prompt=True,
           tokenize=True,
           enable_thinking=False,
       )

   a = chat("1+1 等于几？只回答数字。")
   b = chat("把下面这句话翻译成英文，只输出译文："
            "今天下午三点，我们在图书馆门口集合，然后一起去看电影。")
   params = [SamplingParams(max_tokens=32), SamplingParams(max_tokens=40)]
   out = llm.generate([a, b], params)
   print(repr(out[0]["text"]))
   print(repr(out[1]["text"]))
   row = llm.token_pool[0, : len(b)].tolist()
   print([(i, b[i], row[i]) for i in range(len(b)) if row[i] != b[i]])
   llm.shutdown()
   ```

   开 overlap 时应该看到 A 的输出多了一个 `'\n'`、B 的译文里没有 movie，最后一行打印出 `[(27, 100378, 198)]`；关掉 overlap 后这三处都恢复正常。

   再把 `params` 里 A 的参数换成 `SamplingParams(max_tokens=3, ignore_eos=True)`，让 A 按长度结束。开 overlap 时最后一行同样打印 `[(27, 100378, 198)]`，这次的 198 是 A 真正的最后一个 token。

4. **看服务模式丢掉的最后一个 token。** 先用实测时的参数起服务：

   ```bash
   python -m minisgl --model Qwen/Qwen3-0.6B --max-running-requests 4 \
     --cuda-graph-max-bs 4 --memory-ratio 0.5 --max-seq-len-override 4096
   ```

   另开一个终端，发一个流式请求：

   ```bash
   curl -sN localhost:1919/generate -H 'Content-Type: application/json' \
     -d '{"prompt": "The capital of France is", "max_tokens": 8, "ignore_eos": true}'
   ```

   数一数 `data: [DONE]` 之前有几行，再加上 `MINISGL_DISABLE_OVERLAP_SCHEDULING=1` 重启服务发一次。上面的实测表里有答案：开 overlap 少一行，少的正是 ` Rome`。

5. **挑战：修掉它们。** 下面三处最好一起改。第 2 处离不开第 1 处，单独改会引出新问题；第 1、3 处单独改只是修得不完整：
   - **结束判断改看 CPU 这一侧的长度**：收尾时 `append_host` 之后，用 `len(req.input_ids) >= req.max_device_len` 判断是否到了 `max_tokens`，不再看已经被下一批推进过的 `can_decode`。这样结束标志不再早到，按长度结束的请求也要等最后一批收尾时才还表行。
   - **不给多算的那一步发回复**：收尾时跳过已经在 `finished_reqs` 里的请求，不调 `append_host`，也不生成 `DetokenizeMsg`。这一条必须和上一条一起改，否则按 `max_tokens` 结束的请求，真正的最后一个 token 也会因为请求已经在 `finished_reqs` 里而被跳过。
   - **以 EOS 结束的请求晚一轮还表行**：先把表行记下来，到下一轮收尾、`copy_done.synchronize()` 之后统一还掉。要按轮来还，不要等在批里再遇到这个请求时才还：下一批如果是 prefill 批，里面根本没有它，这一行就永远还不回去了。还要注意一个细节：`copy_done` 是在 `Engine.forward_batch` 末尾记录的，写 `token_pool` 的那一行在 `_forward` 里、排在它之后，所以 `synchronize()` 返回时这次写入严格来说不一定执行完了。要让这个修法严格成立，还得把写入挪到记录事件之前，或者在写入之后再记一个事件。按长度结束的请求改完第一条之后，也是在最后一批的 `copy_done` 之后还表行，同样有这个细节。

   改完后重跑第 3 步的两组参数和第 4 步，overlap 开和关的输出应该完全一致。再跑一遍 `benchmark/offline/bench.py`，确认吞吐没有明显下降。完整的思路和验收标准见[毕业项目](../../appendix/capstone/) 1。

</Steps>
