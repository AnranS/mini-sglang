读完整的代码，看到的是结果；读 git 历史，看到的是顺序：作者先写什么、后写什么，哪些东西第一版就定型了，哪些改过好几次。这一页给两条路：

- **从零搭起来**：15 站。前 14 站从第一个 commit 走到支持 radix cache，都在 2025-09-08 到 09-15 这一周里；最后一站是五个月后的 `page_size > 1`。每站列出这个 commit 带来了什么（以 `git show` 的 diff 为准）和几个阅读问题。
- **修 bug 练习**：7 个上游修复 commit。先读修复前的代码自己找 bug，再看参考答案。

## 怎么用这一页

仓库一共 174 个 commit。最新的 3 个（`04e48db`、`d077e09`、`3b3c403`）是本 fork 加的文档，不属于作者的历史；作者的最后一个 commit 是 `9a91cfa`，共 171 个。

几种常用的看法：

```bash
git show --stat 6d6df1c              # 这个 commit 动了哪些文件、多少行
git show 6d6df1c -- python/minisgl/engine/engine.py   # 只看某个文件的改动
git show 6d6df1c:python/minisgl/engine/engine.py      # 看那个时刻某个文件的全文
git diff 6d6df1c 9a91cfa -- python/minisgl/engine/engine.py  # 和最新版对比
git worktree add ../minisgl-old 900ed45   # 在旁边检出一份旧版本慢慢翻，不影响当前目录
```

<Aside type="caution" title="只读，不要跑">
早期版本依赖的库、目录结构和今天都不一样（比如 kernel 绑定在 `9c53b69` 改用 tvm-ffi，`config/context.py` 后来改名），检出来多半跑不起来。这一页的练习都是读代码。
</Aside>

每站的「行数」用的是 `git show --stat` 最后一行的增删数，包括测试和头文件。

## 路线二：修 bug 练习

下面 7 题都来自上游合并的修复。做法一样：先用 `git show <sha>^:<文件>` 读修复**之前**的代码，按提示找出 bug、想好怎么修，再展开参考答案，最后用 `git show <sha>` 对照真正的修复。题目大致从易到难排。

### 练习 1：LM head 的 all-gather

修复 commit：[`7c59f4d`](https://github.com/sgl-project/mini-sglang/commit/7c59f4df85dfc938915249e147d948399dc29fff)（#98），2026-03-10，改了 1 行。相关章节：<StageLink id="s9" />。

```bash
git show 7c59f4d^:python/minisgl/layers/embedding.py   # 看 ParallelLMHead.forward
```

现象：TP 大于 1 时，一次只发一个请求输出正常，多个请求一起跑就开始胡言乱语。

提示：写出 all-gather 之后 `output_tensor` 每一步的形状。词表被切成 `tp_size` 段，第 `r` 张卡算的是第 `r` 段。

<Answer>
all-gather 之后 `view` 成 `(tp, bs, V/tp)`。旧代码 `movedim(0, -1)` 得到的是 `(bs, V/tp, tp)`，再 `reshape` 成 `(bs, V)`，每一行变成「第 0 段的第 0 个、第 1 段的第 0 个……」交错排列，而不是第 0 段整段接第 1 段整段。正确的做法是 `permute(1, 0, 2)` 得到 `(bs, tp, V/tp)`，`contiguous()` 之后再 `reshape`，修复就是这样改的。

bs 为 1 时走的是前面单独的分支：`(tp, 1, V/tp)` 在内存里本来就是按卡连续排的，直接 `view(1, -1)` 就对了。所以单请求测试发现不了这个 bug。用 `git log -S "movedim(0, -1)"` 可以查到它是第 9 站 `80e7cfd` 引入的，存在了将近半年。
</Answer>

### 练习 2：decode batch 的顺序

修复 commit：[`9a91cfa`](https://github.com/sgl-project/mini-sglang/commit/9a91cfafe754aa85daee49998176275667eb58f2)（#113），2026-05-17，改了 1 行。相关章节：<StageLink id="s9" />。

```bash
git show 9a91cfa^:python/minisgl/scheduler/decode.py   # 看 schedule_next_batch
git show 9a91cfa^:python/minisgl/core.py               # 看 Req 的定义
```

提示：每个 TP rank 各有一个 scheduler 进程，各自独立地组 batch。`running_reqs` 是什么容器？里面元素的哈希值怎么来的？

<Answer>
`running_reqs` 是 `Req` 的 `set`，`Req` 是 `@dataclass(eq=False)`，哈希用的是对象 id，也就是内存地址。不同进程里同一个请求的对象地址不同，`list(self.running_reqs)` 的顺序也就可能不同。于是两张卡上 batch 第 `i` 行对应的是不同的请求，行并行层做 all-reduce 时会把不同请求的部分和加到一起，输出全错。

修复改成 `sorted(self.running_reqs, key=lambda req: req.uid)`。uid 由 API server 的 `FrontendManager.new_user()` 分配（<StageLink id="s8" />），分词进程只是往下传，所以所有 rank 看到的都一样。prefill 没有这个问题，因为等待队列是按到达顺序的列表。
</Answer>

### 练习 3：每张卡各自采样

修复 commit：[`690f55a`](https://github.com/sgl-project/mini-sglang/commit/690f55a342076e22ce4deb271424c681eb84151b)（#88），2026-02-26，加了 1 行。相关章节：<StageLink id="s9" />。

```bash
git show 690f55a^:python/minisgl/engine/engine.py   # 看 Engine.__init__ 和 forward_batch
```

现象（上游 issue #84）：TP=2、temperature 大于 0 时，rank 0 已经结束的请求，rank 1 还在接着跑，显存迟迟不释放。PR 在 GitHub 上的标题因此是「Fix GPU memory leak caused by output inconsistency」；squash 进仓库的 commit 标题换成了原因：「Fix sampler inconsistency due to uninitialized random seed」。

提示：LM head 的 all-gather 之后，每张卡手里的 logits 一样吗？谁在采样？采样的随机数从哪里来？

<Answer>
all-gather 之后每张卡都有完整、相同的 logits，而且每张卡都独立调用采样。FlashInfer 的采样从 PyTorch 默认 CUDA 生成器取种子和偏移。只要各 rank 的生成器状态不同，temperature 大于 0 时就会采出不同的 token：rank 0 采到 EOS 结束了请求，rank 1 没采到，还在继续 decode。之后两边的 batch 不再一致，通信也对不上了。

修复是在 `Engine.__init__` 里加 `torch.manual_seed(42)`，让所有 rank 的生成器从同一个状态出发，此后每一步消耗的随机数一样多，采样结果也就一致。修复前各 rank 的生成器状态**为什么**会不同，本页没有核实。另一种修法是只让 rank 0 采样再广播，代价是每步多一次通信。
</Answer>

### 练习 4：按页驱逐的单位

修复 commit：[`dae78f6`](https://github.com/sgl-project/mini-sglang/commit/dae78f6bb97d5c5aaadbc0772fc964d48a8ee726)（#80），2026-02-22，改了 2 行，另加 198 行测试 `tests/core/test_cache_allocate.py`。相关章节：<StageLink id="s4" />、<StageLink id="s6" />。

```bash
git show dae78f6^:python/minisgl/scheduler/cache.py   # 看 CacheManager._allocate
```

提示：这是第 14 站 `5e52ef3` 引入 `page_size > 1` 的第二天。`evict` 的参数和返回值是 token 还是页？`_free_slots` 里存的是什么？

<Answer>
`_free_slots` 存的是每个空闲页的**起点**，一个元素代表一页；前缀缓存的 `evict(size)` 按 **token** 计数，返回的也是被驱逐的每个 token 的位置。旧代码 `evict(needed_pages - free_pages)` 把页数当 token 数传进去，驱逐得太少；又把返回的所有 token 位置原样拼进 `_free_slots`，每个 token 位置都被当成一页的起点。结果是分出去的「页」互相重叠，不同请求的 KV 写到同一块显存里。

修复是 `evict((needed_pages - free_pages) * self.page_size)`，再用 `evicted[:: self.page_size]` 只取每页的起点。这依赖前缀缓存里的节点总是按整页存的，第 14 站的「按页对齐往前缀缓存里插」保证了这一点。
</Answer>

### 练习 5：max_seq_len 向上对齐

修复 commit：[`ab5d260`](https://github.com/sgl-project/mini-sglang/commit/ab5d260c357fed20c4b8065fe8afcf753a8610bf)（#68），2026-02-17。相关章节：<StageLink id="s4" />。

```bash
git show ab5d260^:python/minisgl/engine/engine.py       # 看 self.max_seq_len 怎么算
git show ab5d260^:python/minisgl/scheduler/scheduler.py # 搜 engine.max_seq_len
```

提示：页表的宽度为什么要对齐到 32？scheduler 拿 `engine.max_seq_len` 做什么？

<Answer>
旧代码是 `self.max_seq_len = _align_up_32(min(config.max_seq_len, self.num_pages))`。对齐是为了让页表每行是 128 字节的整数倍，但同一个值还被 scheduler 当成逻辑上限：检查输入是否过长、算 `max_output_len`。当 KV 总共只有 `num_pages` 个 token 位置、而 `num_pages` 不是 32 的倍数时，向上对齐后的上限超过了 KV 的真实容量，一个本该被拒绝的超长请求会被接纳。

这个 PR 改成向下对齐（小于 32 时保持原值）。同一天 20 分钟后，作者在 [`e7d4f65`](https://github.com/sgl-project/mini-sglang/commit/e7d4f65e8b4e3498bb98f1280ff922fa19fdc47e) 里把它改成了今天的样子：逻辑上限 `max_seq_len = min(config.max_seq_len, num_pages)` 不对齐，只有页表宽度用 `_align_up_32`。把「给调度用的上限」和「给内存布局用的宽度」拆成两个值，比在一个值上取舍更干净。
</Answer>

### 练习 6：分裂节点的时间戳

修复 commit：[`ba3b55c`](https://github.com/sgl-project/mini-sglang/commit/ba3b55c04654a7cf5bea49ce430cbfcce0032bfa)（#124），2026-05-10，加了 1 行。相关章节：<StageLink id="s6" />。

```bash
git show ba3b55c^:python/minisgl/kvcache/radix_cache.py   # 看 _tree_walk 和 RadixTreeNode.split_at
```

提示：一次匹配只命中了某个节点的前半段，节点被分裂成父子两段。新的父节点的 `timestamp` 是多少？驱逐按什么顺序挑节点？

<Answer>
`split_at` 用原节点的 `self.timestamp` 创建新的父节点，也就是上一次访问的旧时间。`_tree_walk` 在完全匹配一个节点时会把它的时间戳更新成 `tic`，但分裂后直接 `return`，刚被命中的前半段就一直带着旧时间戳。

驱逐时只看叶子，按时间戳建小顶堆，最旧的先走；子节点被驱逐后，父节点变成叶子，也进入堆里。于是这段刚被用过的前缀会比它应得的更早被驱逐，下一个相同前缀的请求就要重算。修复是在分裂后加一行 `node.timestamp = tic`。没被命中的后半段保留旧时间戳是对的，它这次确实没被访问。
</Answer>

### 练习 7：FlashInfer 的竞争

修复 commit：[`20fcd7f`](https://github.com/sgl-project/mini-sglang/commit/20fcd7f3c6a1898a61139fae1c97cc7a40bd8d66)（#103），2026-03-13，+7/−5，3 个文件。相关章节：<StageLink id="s5" />、<StageLink id="s7" />。

```bash
git show 20fcd7f^:python/minisgl/attention/fi.py           # 看 _initialize_metadata_once
git show 20fcd7f^:python/minisgl/scheduler/scheduler.py    # 搜 OVERLAP_EXTRA_SYNC
```

现象：开着 overlap 调度、用 FlashInfer 后端时，偶发 illegal memory access；关掉 overlap 就不出现。在此之前，作者在 [`46255ef`](https://github.com/sgl-project/mini-sglang/commit/46255effe4166e7d433766dd98237ebfaadbc82e)（2026-01-06）为 issue #58 加过一个默认关闭的开关 `OVERLAP_EXTRA_SYNC`，打开后每批 forward 前同步一次 scheduler 流。

提示：回到第 7 站的问题。`plan(..., non_blocking=True)` 把 CPU 上的元数据放到哪里、怎样送到 GPU？overlap 下 CPU 比 GPU 领先一批，第二次 `plan` 发生时，第一次的拷贝一定已经执行了吗？

<Answer>
FlashInfer 的 `plan` 先把 CPU 上算好的调度表写进它内部一块复用的 pinned 缓冲，再发一个异步的 H2D 拷贝。这个拷贝排在流上，要等前面的 GPU 工作做完才执行。overlap 调度下 CPU 发射完第 N 批就去准备第 N+1 批，第 N+1 次 `plan` 改写 pinned 缓冲时，第 N 次的拷贝可能还没执行，于是第 N 批拿着第 N+1 批的调度表去算，轻则结果不对，重则越界访问（<StageLink id="s7" /> 讲过同一件事）。PR 描述里说，这「可能」就是 illegal memory access 的原因。

修复给后端加了一个 CUDA event：每次 `plan` 之后 `record()`，下一次 `plan` 之前 `synchronize()`，只等上一次 `plan` 发出的拷贝完成，不必等整批 forward 结束。`_initialize_metadata_once` 因此从 `staticmethod` 改成普通方法。有了它，`OVERLAP_EXTRA_SYNC` 这个绕过办法就删掉了。按 PR 描述，它可能同时解决了 issue #58、#67、#89 和 #102。
</Answer>
